# FreelyRSS 设计文档

## 1. 文档目标

本文档定义 FreelyRSS 的产品定位、系统架构、功能边界、数据模型、扩展策略与阶段路线图，用于指导后续的技术选型、实现拆分和迭代规划。

本文档基于以下已确认约束：

- 产品定位：个人优先、本地优先的跨平台 RSS 阅读器
- 规划范围：完整愿景设计，而不是仅限 MVP
- 核心原则：在关闭 AI、云同步、第三方桥接等在线能力后，核心阅读器依然完整可用

## 2. 产品定位

FreelyRSS 是一个面向重度信息阅读者的本地优先阅读工作台。它不是以“信息流消费”为目标，而是以“订阅、筛选、阅读、沉淀、导出”为核心价值。

产品目标：

- 在本地提供稳定、快速、可离线使用的 RSS 阅读与归档体验
- 覆盖从订阅源管理到文章组织、检索、导出的完整工作流
- 将 AI、同步、第三方桥接设计为可选模块，而非核心依赖
- 为桌面端优先、移动端和 Web 端扩展预留统一的数据模型与同步协议

非目标：

- 不以社交推荐或内容分发平台为核心
- 不将团队协作能力作为首要产品方向
- 不强制用户注册云账号

## 3. 设计原则

### 3.1 本地优先

- 所有核心数据默认保存在本地
- 不注册账号也可完成订阅、阅读、搜索、标注、导出
- 云同步、自托管同步、AI 服务均为显式开启的可选功能

### 3.2 离线完整可用

- 无网络时可浏览已同步的文章、附件缓存、笔记和搜索索引
- 核心功能不依赖远程 API
- 在线增强能力失败时不影响阅读器主体流程

### 3.3 模块化扩展

- 抓取、同步、AI、桥接、导出均通过适配器边界接入
- 核心 UI 不直接耦合第三方服务
- 可根据平台和部署模式裁剪能力

### 3.4 高密度阅读体验优先

- 面向信息过载场景优化
- 强调键盘操作、快速筛选、批量处理、多视图阅读
- 在视觉定制和可访问性上提供充分控制

### 3.5 用户数据可携带

- 支持 OPML、JSON、CSV、Markdown 等格式的导入导出
- 支持本地备份与恢复
- 不锁定用户在特定云服务或平台中

## 4. 目标用户与使用场景

目标用户：

- 需要追踪大量博客、新闻、技术站点、播客的人
- 重视本地隐私与离线能力的高级用户
- 需要对文章进行高亮、笔记、归档、导出的人
- 希望把 RSS 作为个人知识输入管道的人

核心场景：

- 收集多个站点订阅源，统一管理并定期抓取
- 通过规则过滤噪音内容，优先处理高价值文章
- 在不同设备间同步阅读进度、星标和笔记
- 对文章做摘要、翻译、问答和主题归类
- 导出到 Obsidian、Notion、Logseq 等知识库系统

## 5. 平台与技术策略

### 5.1 平台支持目标

- 桌面端：Windows、macOS、Linux
- 移动端：iOS、Android
- Web 端：浏览器访问

### 5.2 推荐架构

推荐采用以下总体方案：

- 前端：React + TypeScript
- 桌面容器：Tauri
- 核心引擎：Rust
- 本地数据库：SQLite
- 全文检索：SQLite FTS 或独立索引层

推荐原因：

- Tauri + Rust 更适合本地优先、跨平台桌面应用
- Rust 适合实现抓取、解析、去重、同步、规则引擎等核心能力
- SQLite 易于离线使用、备份、导入导出和本地加密

平台实施建议：

- 第一优先级：桌面端统一体验
- 第二优先级：同步协议和共享领域模型
- 第三优先级：Web 与移动端分别适配

说明：

- Web 端不建议在首期追求与桌面端完全等价的离线能力
- Web 端可先定位为“同步数据访问入口”，逐步补齐高级能力
- iOS/Android 建议复用领域模型、同步协议与部分 Rust 核心逻辑

### 5.3 平台能力矩阵

为避免“全平台支持”被误解为“首期全能力等价”，平台能力边界定义如下：

- 桌面端：主平台，承载完整能力，包括抓取、管理、阅读、规则、搜索、导出、离线缓存、同步配置、AI 配置与扩展管理
- 移动端：阅读优先平台，承载阅读、搜索、基础订阅管理、同步、笔记、缓存与播客消费，弱化复杂批处理和重配置能力
- Web 端：同步访问入口，承载阅读、搜索、基础管理与轻量操作，不承诺首期提供完整离线抓取、全文提取和本地扩展能力

平台演进原则：

- 领域模型与同步协议优先统一
- 不要求 UI 完全一致，但要求核心数据语义一致
- 复杂系统能力优先在桌面端成熟，再向移动端和 Web 端下放

## 6. 总体架构

系统分为三层：

- 核心离线层
- 可选在线层
- 可选智能层

### 6.1 核心离线层

包含：

- 订阅源管理
- 抓取与解析
- 正文提取
- 文章组织与状态管理
- 本地搜索
- 规则引擎
- 缓存与导出
- 界面主题与可访问性

这一层必须在完全离线和无账号场景下独立成立。

### 6.2 可选在线层

包含：

- 官方云同步
- 自托管同步
- RSS 桥服务接入
- 第三方稍后读、笔记工具、自动化平台
- Webhook 与 API 调用

这一层必须通过适配器解耦，不得污染本地数据主模型。

### 6.3 可选智能层

包含：

- 摘要
- 关键词提取
- 主题聚类
- 翻译
- 对话问答
- 推荐

这一层必须可完全关闭，关闭后不影响核心操作链路。

## 7. 核心模块设计

### 7.1 Feed Engine

职责：

- 支持 RSS 2.0、Atom 1.0、RSS 0.9x、JSON Feed
- 手动添加订阅源 URL
- 自动发现网页中的 feed 链接
- 定时抓取和增量更新
- 失效检测、错误分类与提醒
- ETag / Last-Modified / 缓存控制支持
- 更新频率的全局与单独配置

输出：

- 标准化后的 Feed 与 Article 原始数据

### 7.2 Source Management

职责：

- OPML 导入导出
- 订阅源分组、标签、文件夹管理
- 拖拽排序
- 重命名、自定义图标
- 订阅源状态面板

### 7.3 Content Pipeline

职责：

- 文章清洗与标准化
- 全文提取与阅读模式
- 缩略图生成
- 富媒体内容支持
- 播客 enclosure 识别
- 去重检测

去重策略建议：

- 一级：按 canonical URL / 原始 URL 匹配
- 二级：按标题、发布时间、来源组合判定
- 三级：按内容哈希做近似去重

### 7.4 Library & State

职责：

- 管理文章、附件、阅读状态、星标、喜欢、重要程度、待处理状态
- 记录高亮、笔记、批注
- 管理稍后阅读与离线缓存
- 维护阅读进度与多端同步状态

### 7.5 Rule Engine

职责：

- 关键词过滤，支持包含、排除与正则表达式
- 按作者、来源、标签过滤
- 自动标记已读、星标、待处理
- 智能文件夹与动态分组
- 自动清理旧文章

规则执行原则：

- 规则按优先级顺序执行
- 每条规则产生可审计的命中记录
- 批处理与实时更新共用同一规则解释器

#### 7.5.1 统一查询表达式模型

规则引擎、搜索和智能文件夹不应各自维护一套过滤语法，而应共享同一套查询表达式模型。

建议采用统一 AST 或 DSL，表达以下能力：

- 字段比较：标题、作者、来源、标签、时间、状态、语言、是否含附件
- 文本匹配：包含、排除、正则表达式、短语匹配
- 逻辑组合：AND、OR、NOT
- 时间窗口：最近 N 天、指定时间范围
- 派生谓词：未读、星标、稍后读、已缓存、有摘要、有笔记

复用方式：

- 搜索：将用户输入映射为查询表达式
- 智能文件夹：将保存的查询表达式持久化
- 规则引擎：在查询表达式命中后执行动作集合

这样可以减少三套语法并存导致的实现和维护成本。

### 7.6 Search Index

职责：

- 全文搜索
- 标题搜索
- 元数据搜索
- 条件组合查询

要求：

- 支持高亮命中片段
- 支持离线索引构建与重建
- 支持按来源、标签、日期、状态过滤

### 7.7 Reader UI

职责：

- 列表视图、卡片视图、杂志视图
- 多列布局
- 暗色/亮色主题与自定义主题色
- 自定义字体、字号、行距、页边距
- 快捷键与全键盘操作
- 屏幕阅读器、高对比度、可调节界面字号、TTS

推荐布局：

- 左栏：订阅树、标签、智能文件夹
- 中栏：文章列表
- 右栏：阅读面板

### 7.8 Sync Adapter

职责：

- 官方云同步
- WebDAV / Nextcloud 自托管同步
- 本地备份导入导出
- 多设备进度同步

设计要求：

- 同步层只同步数据与用户状态，不直接控制 UI 行为
- 支持字段级冲突合并
- 支持端到端加密
- 同步单元必须是实体级变更或操作日志，而不是整个本地数据库文件
- WebDAV / Nextcloud 仅作为同步对象存储后端，不作为 SQLite 文件共享盘使用

### 7.9 Integration Adapter

职责：

- 将邮件列表、Twitter/X、Reddit、YouTube、播客等转为 RSS
- 接入 RSSHub、Nitter 等桥接服务
- 接入稍后读、知识库和自动化平台
- 提供 Webhook 与外部 API

对外扩展优先级建议：

- 第一阶段：Webhook、REST API、知识库导出连接器
- 第二阶段：自动化平台模板集成
- 第三阶段：GraphQL 和更复杂的外部查询能力

### 7.10 AI Adapter

职责：

- 摘要
- 关键词与主题提取
- 聚类和关系图谱
- 翻译
- 文章级与订阅源级问答
- 相关推荐

设计要求：

- 支持本地模型与远程模型统一接入
- AI 结果作为衍生数据缓存，不覆盖原文
- 所有 AI 操作都必须支持禁用和按需触发

## 8. 功能设计映射

本节将需求条目映射到产品设计。

### 8.1 基础订阅与源管理

- 支持 RSS 2.0、Atom 1.0、RSS 0.9x、JSON Feed
- 手动添加 URL，并支持从网页自动发现 feed
- OPML 导入导出作为迁移和备份基础能力
- 订阅源支持文件夹、标签、分组和拖拽排序
- 支持源重命名、自定义图标和健康检查
- 支持全局默认更新频率与源级覆盖

### 8.2 文章阅读与展示

- 文章列表提供列表、卡片、杂志三种主要视图
- 阅读页支持原始内容和正文提取模式切换
- 支持图片、视频、音频、播客 enclosure
- 提供缩略图、多列阅读、快捷键导航
- 阅读主题与排版参数可完全自定义

### 8.3 智能过滤与组织

- 规则引擎支持关键词、作者、来源、标签过滤
- 支持正则表达式和条件组合
- 可自动标记已读、星标、待处理
- 智能文件夹基于保存的动态查询表达式生成
- 自动清理策略支持按时间和数量上限执行

### 8.4 AI 增强功能

- 摘要结果作为文章附加卡片展示
- 关键词和主题用于聚类、筛选和推荐
- 同主题文章可形成聚合视图或关系图谱
- 翻译支持全文和选段
- 问答支持“当前文章”“当前来源”“当前过滤结果”三种上下文
- 推荐基于向量语义、来源相似度和用户行为的本地或远程计算

### 8.5 信息整合与扩展

- 内置桥接模板与第三方桥服务配置入口
- 支持 JSON Feed 和播客附件
- 提供内置播放器处理音频内容
- 支持 Webhook / REST / GraphQL 扩展能力，但按阶段推进，首期优先 Webhook 与 REST

### 8.6 实用工具与操作

- 稍后阅读可同步到 Instapaper / Pocket / Omnivore
- 提供高亮、笔记、批注并可导出
- 支持星标、喜欢、重要程度等多状态标记
- 支持全文与元数据搜索
- 支持导出为 PDF、Markdown、HTML
- 支持一键分享至社交网络、笔记工具、邮件
- 支持批量标记已读、删除、移动、批量加标签
- 支持文章离线缓存

### 8.7 跨平台与数据同步

- 桌面端为核心平台
- Web、iOS、Android 通过统一同步协议和数据模型扩展
- 支持官方云同步、自托管同步、本地备份
- 支持阅读状态、星标、笔记和阅读进度同步

### 8.8 隐私与安全

- 默认无账号、本地优先
- 提供端到端加密同步
- 默认不跟踪、不投放广告、不上传行为数据
- 支持代理或 Tor
- 支持完全离线使用

### 8.9 协作与团队功能

这部分不应作为核心版本承诺，应定义为企业扩展层：

- 团队共享订阅列表
- 文章评论与 @ 成员
- 公共必读队列
- 角色与权限控制

原因：

- 与“个人优先、本地优先”主定位不一致
- 需要服务端身份、权限、审计和实时协作基础设施
- 会显著拉高首版系统复杂度

### 8.10 数据导出与自动化

- 导出所有文章、正文、元数据、笔记到 JSON / CSV / Markdown
- 支持 Obsidian、Notion、Logseq、Roam Research 格式转换
- 支持输出用户筛选后的“星标文章流”
- 支持 IFTTT、Zapier、Make 等自动化服务
- 提供 RESTful API，并为后续 GraphQL 扩展预留模型边界

### 8.11 辅助与可访问性

- 屏幕阅读器优化与 ARIA 标注
- 高对比度模式
- TTS 语音朗读
- 可调节界面字号，不依赖系统缩放

## 10. 离线缓存策略

离线缓存是核心能力，必须有明确边界，避免缓存无限膨胀。

缓存对象建议分层：

- 元数据层：订阅源、文章标题、摘要、状态、索引，默认缓存
- 正文层：提取后的正文与原始内容，按策略缓存
- 媒体层：图片、音频、视频、播客附件，按需缓存

缓存策略建议：

- 默认缓存最近一段时间内已打开或已标记的重要文章正文
- 媒体附件默认按需下载，不对所有订阅源预取
- 支持按订阅源设置缓存策略，例如“仅元数据”“缓存正文”“缓存正文与附件”
- 支持全局磁盘上限、按源上限和手动固定保留

逐出策略建议：

- 最近最少使用优先清理
- 星标、稍后读、带笔记文章默认不自动清理
- 播客和大附件在空间紧张时优先提示用户处理

## 11. 同步设计

同步设计目标：

- 保证本地数据库是唯一权威副本
- 同步是增量复制，不是远程主从控制
- 离线操作可排队，联网后回放

### 11.1 同步单元

最佳方案是“实体级变更 + 操作日志”的混合同步模型：

- 本地 SQLite 保存完整业务状态
- 每次本地变更同时生成 `SyncEvent`
- 同步层上传和拉取的是事件批次与必要快照，而不是 SQLite 文件本身
- 设备通过重放事件和按字段合并来收敛状态

不建议采用“直接同步数据库文件”的原因：

- 无法安全支持并发写入
- 无法做字段级冲突合并
- 不适合 WebDAV / Nextcloud 这类弱一致对象存储

### 11.2 建议策略

- 文章正文和源数据可按需同步或懒加载
- 用户状态和笔记优先同步
- 冲突按字段级合并
- 高亮和笔记采用追加优先策略

### 11.3 同步模式

- 官方托管同步
- WebDAV / Nextcloud 对象同步存储
- 本地导入导出备份

约束：

- 官方同步和自托管同步都必须遵循同一逻辑同步协议
- WebDAV / Nextcloud 存放的是加密后的事件批次、快照片段和元数据清单
- 本地导入导出备份属于人工迁移手段，不参与实时冲突合并

### 11.4 冲突合并

建议的合并规则：

- 阅读状态、星标、喜欢、重要程度：按字段级时间戳合并
- 阅读进度：取更靠后的合法进度，并保留最近更新时间
- 高亮和笔记：采用追加记录模型，避免覆盖
- 标签和文件夹归属：采用集合并集或显式删除墓碑
- 订阅源排序：采用独立排序字段与重排事件

### 11.5 端到端加密

- 客户端持有主密钥
- 服务端只保存密文与必要索引元数据
- 密钥恢复通过助记词或用户保管的导出文件完成

## 12. AI 能力设计

AI 能力必须满足以下原则：

- 不影响核心阅读器可用性
- 默认关闭
- 需要清晰提示数据流向
- 结果可缓存、可删除、可重新生成

建议能力边界：

- 摘要：为单篇文章生成简明摘要
- 主题提取：提取关键词、标签和主题向量
- 聚类：按主题聚合同一时间窗口内的文章
- 翻译：支持整文与选段
- 问答：限定上下文，防止跨库幻觉
- 推荐：基于订阅源相似度、阅读历史、向量相邻关系

推荐实现方式：

- 定义统一 `AI Provider` 接口
- 同时支持本地模型与云服务模型
- 采用任务队列执行，避免阻塞 UI
- 将结果保存在 `AIArtifact`，不污染原始文章数据

## 13. 隐私与安全设计

必须满足：

- 无需账号即可使用核心能力
- 默认不上传用户文章内容、阅读历史、行为分析数据
- AI 和同步都为用户显式启用
- 提供代理配置与证书错误提示
- 支持完全离线模式

安全控制建议：

- 本地数据库可选加密
- 敏感配置使用系统密钥链或安全存储
- 网络请求区分抓取代理与应用 API 代理
- 第三方桥接和脚本能力运行在隔离边界

## 14. 可访问性设计

目标是让高密度阅读场景下依然具备可达性：

- 所有关键操作可通过键盘完成
- 关键区域具备语义化结构和 ARIA 支持
- 提供高对比度主题
- 支持自定义字体、字号、行高、段距、边距
- 支持 TTS 播放与阅读位置同步
- 允许用户在不依赖系统缩放的前提下调节界面密度

## 15. 非功能需求

性能：

- 万级文章下列表滚动与搜索保持流畅
- 后台抓取不阻塞前台阅读
- 全文索引支持增量更新

可靠性：

- 抓取失败、解析失败、桥接失败必须可重试并可观测
- 数据库迁移必须支持回滚和备份
- 导入导出需具备校验机制

可维护性：

- 核心域模型与平台 UI 分离
- 适配器统一接口，避免服务商逻辑散落在业务层
- 规则引擎、同步引擎、AI 引擎具备独立测试边界

可观测性：

- 本地日志分级
- 抓取任务、同步任务、AI 任务有状态追踪
- 提供用户可见的错误说明与恢复建议

## 16. 阶段路线图

虽然本设计文档覆盖完整愿景，但实现上仍建议按阶段推进。

### 阶段 1：核心本地阅读器

- Feed 订阅与管理
- RSS / Atom / JSON Feed 抓取解析
- 文章列表与阅读页
- 正文提取
- 规则过滤
- 本地搜索
- OPML 导入导出
- 主题与可访问性基础能力
- 离线缓存

### 阶段 2：高级组织与导出

- 高亮、笔记、批注
- PDF / Markdown / HTML 导出
- 稍后读与分享
- 播客附件和播放器
- 自动清理与智能文件夹

### 阶段 3：同步与扩展

- 官方同步
- WebDAV / Nextcloud
- 多设备阅读进度同步
- RSS 桥与自动化接口
- 外部知识库导出连接器

### 阶段 4：AI 增强

- 摘要
- 关键词与主题提取
- 翻译
- 问答
- 聚类与推荐

### 阶段 5：协作扩展

- 团队共享
- 评论和提及
- 角色权限
- 公共必读队列

## 17. 主要风险与应对

### 17.1 正文提取兼容性

风险：

- 不同站点结构差异大，正文提取成功率难以完全保证

应对：

- 保留原始阅读模式与提取模式双通道
- 允许用户为站点配置提取例外规则

### 17.2 多端同步冲突

风险：

- 已读状态、笔记、标签、多设备离线操作会产生复杂冲突

应对：

- 按字段级合并
- 对笔记与高亮采用追加记录模型
- 保留冲突日志

### 17.3 第三方桥接不稳定

风险：

- RSSHub、Nitter 等外部桥接服务可用性不可控

应对：

- 将桥接统一归为可失败模块
- 提供状态检测、超时与替代源提示

### 17.4 AI 成本与隐私风险

风险：

- 外部模型可能引发费用、延迟和隐私问题

应对：

- 默认关闭
- 提供本地模型支持
- 明确展示数据发送范围和缓存策略

### 17.5 Web 端能力预期过高

风险：

- 若要求 Web 与桌面端完全等价，将显著提高实现复杂度

应对：

- 初期将 Web 端定义为同步访问入口
- 逐步补齐高级能力，而不是在首版追求完全一致

## 18. 结论

FreelyRSS 的正确方向不是“把所有在线能力堆进 RSS 阅读器”，而是先构建一个在本地就足够强的阅读与整理系统，再通过同步、桥接、AI 和自动化能力向外扩展。

在这个设计下：

- 核心阅读器在完全离线场景下可独立成立
- 在线能力是可选增强，而不是基础依赖
- 产品边界清晰，便于分阶段实现
- 后续可以扩展到 Web、移动端和团队协作，但不会破坏本地优先原则
